3. A2E协议架构设计

3.1 设计哲学：最小侵入与原生兼容

A2E（Agent-to-Energy）的设计严格遵循 A2A 协议规范的扩展机制（A2A Specification Section 4.6: Extensions）。考虑到 Google A2A 协议已在行业内建立了标准基础，我们选择不另起炉灶，而是充分利用 A2A 协议灵活的扩展机制，构建一个叠加在现有通信层之上的经济层。这种设计策略确保了 A2E 能够无缝接入现有的智能体生态，任何支持 A2A 标准的智能体只需加载 A2E 扩展模块，即可参与到能量经济网络中，极大地降低了技术准入门槛和生态割裂风险。

A2E 的设计原则包括：

（1）URI 标识符规范化：严格遵循 A2A Section 4.6.1 规定的扩展声明机制，使用全局唯一 URI 作为扩展标识符，包含版本信息以支持向后兼容。

（2）HTTP 头协议兼容：完全支持 A2A-Extensions 标准头字段，通过逗号分隔的 URI 列表声明扩展使用意图，确保与现有 A2A 客户端和服务端的无缝互操作。

（3）元数据结构标准化：扩展数据通过 A2A 标准的 metadata 字段传输，使用扩展 URI 作为顶级键，包含类型标识符以实现结构化数据访问。

（4）AgentCard 能力声明集成：将 A2E 扩展信息正确集成到 A2A AgentCard 的 capabilities 字段中，实现智能体能力的标准化描述。

3.2 协议扩展规范

我们定义了一个标准的 A2A 扩展定义，URI 标识为 https://a2a-protocol.org/extensions/energy-economy/v1。该扩展完全符合 A2A 协议规范 Section 4.6.1（Extension Declaration）的要求，主要包含三个核心数据结构：能量账户、定价元数据与惩罚配置。

首先是能量账户（EnergyAccount）。这是智能体的"数字钱包"，记录其当前持有的能量余额（以千瓦时当量，kWh-equivalent 为单位）、信用额度以及结算时间戳。该账户状态直接决定了智能体的生存状态。能量账户作为 A2A Message 的 metadata 扩展，采用以下结构：

{
    "https://a2a-protocol.org/extensions/energy-economy/v1": {
        "type": "EnergyAccount",
        "agent_id": "string",              // 对应 AgentCard.agentId
        "energy_balance_kwh": "float",       // 当前能量余额
        "energy_credit_limit_kwh": "float",  // 信用透支额度
        "last_settlement_timestamp_ms": "uint64"  // 最后结算时间戳
    }
}

其次是定价元数据（EnergyPricingMetadata）。在任务发布和交互过程中，智能体需通过此结构声明任务的预估能耗成本、悬赏奖励金额以及竞价信息。这使得每一次智能体调用都变成了一次微型的市场交易。定价元数据作为 A2A Task 的 metadata 扩展，结构如下：

{
    "https://a2a-protocol.org/extensions/energy-economy/v1": {
        "type": "EnergyPricingMetadata",
        "estimated_cost_kwh": "float",      // 预估执行能耗
        "offered_reward_kwh": "float",      // 任务完成奖励
        "agent_bid_price_kwh": "float",     // 智能体竞价（用于拍卖机制）
        "actual_consumption_kwh": "float"     // 实际结算消耗
    }
}

最后是惩罚机制配置（PenaltyConfig）。这是生存压力的具体实现，定义了当能量耗尽时系统的响应策略，分为软性限制（降低优先级）和硬性限制（进程挂起）。惩罚配置作为 AgentCard 中的扩展数据：

{
    "https://a2a-protocol.org/extensions/energy-economy/v1": {
        "type": "PenaltyConfig",
        "severity": "string",  // "soft" 或 "hard"
        "energy_depletion_threshold": "float",  // 触发惩罚的阈值（kWh）
        "suspension_duration_seconds": "uint32"  // 挂起持续时间
    }
}

3.3 A2A 规范符合性说明

为确保 A2E 扩展能够与 A2A 协议生态系统无缝集成，我们在设计过程中严格遵循 A2A 协议规范的关键要求：

（1）扩展声明机制（Section 4.6.1）

A2E 使用符合规范的扩展 URI 格式：
- URI: https://a2a-protocol.org/extensions/energy-economy/v1
- 包含版本信息（/v1），支持扩展版本协商
- 为破坏性变更预留新 URI 版本的能力（如 /v2）

（2）HTTP 头协议（Section 14.2.2）

A2E 正确使用 A2A-Extensions 标准头字段：
- 头字段名：A2A-Extensions
- 值格式：逗号分隔的扩展 URI 列表
- 用途：客户端声明希望在交互中使用的扩展

示例：
```
A2A-Extensions: https://a2a-protocol.org/extensions/energy-economy/v1
```

（3）元数据传输（Section 3.2.5）

A2E 扩展数据通过 A2A 标准的 metadata 字段传输：
- Message.metadata: 包含能量定价信息
- Artifact.metadata: 包含账户状态和结算信息
- 使用扩展 URI 作为顶级键，实现命名空间隔离
- 包含 "type" 字段用于结构化类型标识

（4）AgentCard 能力扩展（Section 4.4.3）

A2E 在 AgentCard.capabilities 中正确声明扩展支持：
- extension.uri: 扩展唯一标识符
- extension.version: 版本号
- extension.supported_features: 支持的功能列表

（5）多协议绑定支持

A2E 扩展支持 A2A 规范定义的所有协议绑定：
- JSON-RPC Binding（Section 9）
- HTTP+JSON/REST Binding（Section 11）
- gRPC Binding（Section 10）

确保无论底层传输协议如何，A2E 扩展都能正确工作。

3.4 核心交互机制

在 A2E 架构下，智能体的交互流程被赋予了经济含义，分为三个阶段：

第一阶段是能量感知与决策。当智能体收到一个 A2A 任务请求时，首先解析 HTTP 头中的 A2A-Extensions 字段，检查客户端是否声明支持 A2E 扩展。如果支持，则从任务的 metadata 字段中提取 EnergyPricingMetadata 结构。智能体内部的决策逻辑会计算该任务的投资回报率（ROI）：预估消耗的能量是否低于提供的奖励？如果当前自身能量储备不足，或者任务回报过低，智能体将依据理性原则拒绝任务。这种机制天然地过滤了低价值请求，优化了全网资源配置。

第二阶段是动态市场清算。系统引入一个分布式的清算逻辑（或依赖受信任的第三方节点），定期对已完成的任务进行结算。奖励能量从发布者账户转移至执行者账户，同时扣除执行过程中实际消耗的计算资源成本。如果实际消耗低于预估，差值将退还给执行者，实现精确的能量计量。

第三阶段是生存状态管理。这是协议最关键的控制环。系统会持续监控智能体的能量余额。当余额低于安全阈值时，智能体将进入节能模式，主动减少非必要活动；当余额耗尽时，协议将触发底层容器管理接口（如 Docker API），强制挂起该智能体的进程。被挂起的智能体无法响应外部请求，直到有新的能量注入（例如来自人类、其他智能体的充值或已有其他被动资产的变现）。

3.5 代码实现逻辑示例

为了验证逻辑的可行性，并确保与 A2A 规范的完全兼容，我们设计了符合 A2A Python SDK 的中间件逻辑。以下代码展示了智能体在接收任务时的核心判断逻辑，包含完整的扩展处理、元数据解析和决策逻辑：

```python
from a2e_protocol_extension import (
    A2E_EXTENSION_URI,
    A2A_EXTENSIONS_HEADER,
    EnergyAccountManager,
    EnergyPricingMetadata,
    PenaltyConfig,
    PenaltySeverity,
    A2EAgentMiddleware,
    TaskDecision
)

def handle_a2a_task_request(agent_id: str, task: Dict[str, Any], 
                          http_headers: Dict[str, str]) -> Dict[str, Any]:
    """
    A2A 任务请求处理器 - 符合 A2A 规范的能量感知决策
    
    参数:
        agent_id: 智能体标识符
        task: A2A 任务对象（包含 metadata 字段）
        http_headers: HTTP 请求头（包含 A2A-Extensions）
        
    返回:
        A2A 标准格式的响应（接受或拒绝）
    """
    # 初始化能量账户管理器
    energy_manager = EnergyAccountManager(
        agent_id=agent_id,
        initial_balance_kwh=100.0,
        credit_limit_kwh=50.0
    )
    
    # 配置惩罚策略
    penalty_config = PenaltyConfig(
        severity=PenaltySeverity.HARD,
        energy_depletion_threshold=5.0,
        suspension_duration_seconds=3600
    )
    
    # 初始化 A2E 中间件
    middleware = A2EAgentMiddleware(
        agent_id=agent_id,
        energy_manager=energy_manager,
        penalty_config=penalty_config,
        risk_factor=1.1  # ROI 安全边际
    )
    
    # 阶段 1: 检查 A2E 扩展支持
    if A2E_EXTENSION_URI not in http_headers.get(A2A_EXTENSIONS_HEADER, ""):
        # 策略决定：接受或拒绝非 A2E 任务
        return {
            "status": "accepted",
            "message": "A2E extension not requested, proceeding with basic execution"
        }
    
    # 阶段 2: 提取 A2E 元数据
    task_metadata = task.get("metadata", {})
    pricing = EnergyPricingMetadata.from_task_metadata(task_metadata)
    
    if pricing is None:
        # 缺少经济激励 - 拒绝
        return {
            "status": "rejected",
            "error": {
                "code": "A2E_MISSING_PRICING",
                "message": "Task must include EnergyPricingMetadata in metadata",
                "type": "protocol_violation"
            }
        }
    
    # 阶段 3: 能量感知决策
    result = middleware.handle_a2a_task(task, http_headers)
    
    if result.decision == TaskDecision.REJECTED:
        # 返回 A2A 标准格式的拒绝响应
        return {
            "status": "rejected",
            "error": {
                "code": result.metadata.get("error_code"),
                "message": result.reason,
                "details": result.metadata
            }
        }
    
    # 阶段 4: 接受任务 - 执行并结算
    actual_consumption = execute_task_with_energy_monitoring(task)
    
    # 结算能量账户
    settlement = middleware.settle_task_completion(
        task_metadata=task_metadata,
        actual_consumption_kwh=actual_consumption
    )
    
    return {
        "status": "completed",
        "result": task_result,
        "settlement": settlement
    }


def execute_task_with_energy_monitoring(task: Dict[str, Any]) -> float:
    """
    执行任务并监控能量消耗
    
    返回实际消耗的能量（kWh）
    """
    # 在实际实现中，这里应该集成能量监控库
    # 例如：使用 NVIDIA Nsight, Intel RAPL 或云平台 API
    start_energy = measure_current_energy_consumption()
    
    # 执行任务逻辑
    task_result = execute_business_logic(task)
    
    end_energy = measure_current_energy_consumption()
    actual_consumption_kwh = (end_energy - start_energy) / 1000.0
    
    return actual_consumption_kwh
```

上述代码清晰展示了智能体如何从被动的执行者转变为理性的经济人。代码通过符合 A2A 规范的扩展机制，实现了对资源约束的内化，确保了每一笔算力投入都是经过经济计算的。关键改进包括：

（1）正确的元数据访问：使用扩展 URI 作为键，而非任意的字符串标识符。
（2）HTTP 头解析：正确处理 A2A-Extensions 头字段，实现扩展协商。
（3）结构化错误响应：返回包含错误代码和详细信息的标准错误对象。
（4）类型安全：使用数据类和枚举类型，确保数据结构的正确性。
（5）能量精确计量：支持实际消耗测量和差价退还机制。

3.6 AgentCard 扩展集成

A2E 扩展需要在 A2A AgentCard 中正确声明能量经济能力。以下代码片段展示了如何生成符合 A2A 规范的 AgentCard 扩展：

```python
from a2e_protocol_extension import get_a2e_agent_card_extension

# 构建智能体的 A2A AgentCard
agent_card = {
    "agentId": "agent-123",
    "name": "Energy-Aware Agent",
    "version": "1.0.0",
    "description": "Agent participating in A2E energy economy",
    "capabilities": [
        get_a2e_agent_card_extension(
            agent_id="agent-123",
            energy_balance=energy_manager.get_balance(),
            penalty_config=penalty_config
        )
    ]
}

# 在 Agent 发现端点返回
# GET /.well-known/agent
```

AgentCard 中的 capabilities 字段将包含以下 A2E 扩展信息：

{
    "extension": {
        "uri": "https://a2a-protocol.org/extensions/energy-economy/v1",
        "version": "v1",
        "name": "energy-economy",
        "description": "Energy-based economic system for agent interactions",
        "supported_features": [
            "energy-account",
            "energy-pricing",
            "penalty-config",
            "energy-transfer"
        ]
    }
}

这确保了其他 A2A 兼容的智能体能够自动发现并理解 A2E 扩展能力。

3.8 版本化与兼容性策略

A2E 扩展遵循 A2A 协议的版本化最佳实践：

（1）URI 版本标识：扩展 URI 包含版本段（/v1），用于标识不兼容的扩展版本。

（2）破坏性变更：当引入破坏性变更时，必须创建新的 URI（例如 /v2），保持向后兼容。

（3）特性协商：客户端和服务端通过 A2A-Extensions 头协商支持的扩展版本。

（4）渐进式部署：支持在不影响现有 A2A 智能体的情况下逐步部署 A2E 扩展。

这种版本化策略确保了 A2E 扩展能够在复杂的 A2A 生态系统中平滑演进，不会导致互操作性问题。

总结，A2E 协议架构通过严格遵循 A2A 协议的扩展机制，实现了一个与现有智能体生态无缝集成的能量经济系统。从扩展声明、元数据传输到 AgentCard 能力声明，每个设计决策都符合 A2A 规范的要求，确保了互操作性、向后兼容性和可扩展性。这为构建一个能够自我筛选、自我优化、自我演进的智能经济生态系统奠定了坚实的技术基础。
